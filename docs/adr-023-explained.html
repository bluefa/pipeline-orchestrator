확정정보 재확정과 연결 테스트를서버가 끝까지 실행합니다.

화면이 추천 조회 → 편집 → 등록 → 테스트 시작 → 폴링을 각각 호출하던 작업을, 복구 가능한 인프라 작업(코드·API의 pipeline) 안으로 옮깁니다. 핵심은 두 가지입니다. 추천 조회와 등록은 Task 하나이고, 테스트 접수 성공은 테스트 성공이 아닙니다. 이 문서는 그 두 문장이 데이터·상태·실패 처리에서 어떤 모양이 되는지를 보여 줍니다.

✓이 문서가 설명하는 범위

  • 백엔드 내부 구현과 H2/fake 검증 반영 — 공통 Task 3개, RECONFIRM·TEST_CONNECTION Recipe, HTTP·TC executor
  • 자동화 검증은 H2 스키마와 fake client 기준입니다 (기존 Terraform/Condition 회귀 포함)
  • 스키마는 JPA annotation 선언 + H2에서의 동작 검증
  • 재시도와 재시작의 경계는 구현된 계약 그대로 §09에 정리했습니다

!아직 확인하지 않은 것

  • 실제 운영 upstream 계약 — 기본 UnavailableInstallationOperationsClient는 capability를 제공하지 않습니다
  • 실제 MySQL에서의 컬럼·인덱스·길이·packet 검증 (H2 결과로 대신하지 않습니다)

01

브라우저가 이어 붙이던 절차를, 하나의 실행이 소유합니다

지금은 사용자가 화면을 떠나거나 탭을 닫으면 절차가 중간에서 끊깁니다. 재확정은 인프라 삭제까지 포함하므로 중간에서 끊기면 “확정정보도 인프라도 없는 상태”가 남습니다. ADR-023은 이 절차를 재시도 가능한 Task 체인으로 옮깁니다.

지금 · 화면이 순서를 기억

각 버튼이 각각의 API를 호출

  • 확정정보 삭제Admin 모달 → CSP별 DELETE 1회
  • 확정정보 입력추천 GET → 편집기 초안 → 등록 POST · 두 호출을 화면이 연결
  • 연결 테스트async POST → latest 실행 4초 폴링 → 사용자가 acknowledgment
  • 인프라INSTALL / DELETE 인프라 작업만 서버가 실행

중간 실패의 복구·재시도·증거는 사람의 기억에 남습니다.

ADR-023 · 실행이 순서를 소유

업무 유형별 인프라 작업이 끝까지 진행

  • RECONFIRMCSP 테라폼 Destroy … → 확정정보 삭제 → 추천 기반 확정정보 입력
  • TEST_CONNECTION요청 키로 시작한 그 실행의 종결만 인정
  • CUSTOM공통 Task 하나만, 또는 같은 정의를 여러 번
  • INSTALL / DELETE기존 유형과 Recipe를 그대로 유지

claim·lease·guarded write-back, 대상당 활성 실행 하나, 종단 상태 부활 금지는 그대로입니다.

RECONFIRM의 DONE은 “새 확정정보 등록 완료”입니다. 인프라 재설치까지 포함하지 않습니다. 재설치는 이어지는 INSTALL 실행에서 확인합니다.
TEST_CONNECTION의 DONE은 “그 실행이 SUCCESS”입니다. 사용자의 업무 완료 확인(acknowledgment)은 여전히 사람이 수행하는 별도 단계입니다.
실패해도 자동 롤백은 없습니다. 이미 커밋된 삭제는 되돌리지 않고, 어디까지 진행됐는지를 남깁니다.

02

“업무가 무엇인가”와 “어떻게 실행되는가”는 다른 축입니다

이 둘을 한 enum에 섞으면 HTTP 한 번으로 끝나는 작업과 수십 분짜리 비동기 테스트가 같은 완료 규칙을 갖게 됩니다. ADR-023은 축을 나눕니다. 화면이 쓰는 업무 유형과 엔진이 쓰는 실행 방식(mechanism)입니다.

업무 축

PipelineType

운영자가 목록에서 고르고 화면이 필터로 쓰는 분류입니다. 별도 RecipeType enum은 만들지 않고 여기에 두 값만 추가합니다.

  • INSTALL · DELETE · CUSTOM 기존
  • RECONFIRM
  • TEST_CONNECTION
실행 축

TaskType mechanism

엔진이 “무엇을 호출하고 언제 끝났다고 판정하는가”를 정합니다. Task 이름을 비교하지 않고 mechanism으로 라우팅합니다.

  • TERRAFORM_JOB · CONDITION_CHECK 기존
  • HTTP_REQUEST
  • TEST_CONNECTION_JOB

HTTP_REQUEST는 코드에 등록된 operation만 호출합니다. 임의 URL·메서드를 입력받는 실행기가 아닙니다. Terraform slot을 쓰지 않더라도 worker 수와 running-pipeline-cap, 호출별 timeout은 동일하게 적용됩니다.

03

재확정 한 건이 흘러가는 모습

CSP와 상황을 고르고 다음 turn 실행을 눌러 보세요. 특히 마지막 Task를 보세요. 추천 GET이 성공해도 완료 Task 수는 늘지 않습니다. GET은 Task 안의 단계이지 Task가 아니기 때문입니다.

이 예시는 진행을 한 줄로 보여 주기 위해 Terraform Task 한 칸을 job 생성 dispatch와 그 뒤의 여러 폴 turn을 합친 요약으로 그립니다. 실제로는 worker 한 번의 외부 호출이 job을 만들면서 동시에 완료시키지 않습니다. 반면 HTTP Task의 GET·POST는 각각 실제로 turn 하나입니다.

    인프라 작업 상태

    0 / 5완료 Task 수 · 호출 수나 경과 시간이 아닙니다

    이번 turn에 일어난 일

    task_confirmation_input · recommendation_body 
    (아직 없음)

    왜 Task 하나인가

    호출은 둘, 작업 단위는 하나

    추천 GET이 성공하면 원문·digest·GET metadata·source attempt 번호·검증된 맥락을 한 번만 저장하고 같은 Task를 IN_PROGRESS로 둡니다. 후속 Task는 BLOCKED입니다. 다음 turn에 같은 Task가 저장된 본문으로 POST하고, 그때 비로소 DONE이 되며 후속 Task가 READY로 승격합니다.

    저장된 본문은 write-once입니다. 등록이 일시 실패해 재시도 READY가 되어도 executor는 이미 저장된 입력을 발견하고 POST부터 재개합니다. 추천 GET을 다시 호출하지 않습니다.

    반대로 새 실행으로 재시작하면 이 스냅샷을 물려받지 않습니다. 새 입력 Task가 새 GET으로 자기 본문을 캡처합니다 (§09).

    입력 유실과 관찰 유실은 다릅니다

    쓰기를 막는 실패 / 복구 가능한 실패

    입력 행이 없으면 EXECUTION_INPUT_MISSING, 본문·digest·맥락이 손상되면 EXECUTION_INPUT_INVALID로 쓰기 API를 호출하지 않고 종결 실패합니다. 이미 IN_PROGRESS인데 본문이 없다면 새 GET으로 “복구”하지 않습니다. 그건 다른 세대의 추천값이 될 수 있습니다.

    반대로 관찰용 task_attempt만 유실되고 입력이 정상이면 POST를 재개할 수 있습니다. guarded write-back에서 현재 attempt가 없으면 복구 생성해 응답을 남깁니다.

    취소·크래시로 폐기된 결과는 “외부에서 아무 일도 없었다”는 증거가 아닙니다. 보존 단위는 정상 guarded write-back에서 채택된 결과입니다. stale token으로 거절된 결과, 취소가 우선한 결과, 커밋 전 크래시한 결과는 기록되지 않지만 upstream에는 이미 도달했을 수 있습니다. 화면은 “커밋된 삭제 단계”와 “확인 불가인 외부 효과”를 구분해 표시해야 합니다. claim token은 DB 쓰기를 막을 뿐 이미 나간 요청을 취소하지 못합니다.

    04

    상태를 늘리는 대신 데이터를 분리합니다

    새 상태 enum은 하나도 추가하지 않습니다. 대신 판정에 반드시 필요한 데이터와 사람이 보는 진단을 다른 테이블로 나눕니다. 아래에서 기준선과 확장을 전환하고, 테이블을 눌러 역할을 확인하세요.

    신규 테이블 기존 테이블 · 컬럼 추가 변경 없음

    관계

    pipeline 1 ─ N task 1 ─ N task_attempt task 1 ─ 0..1 task_confirmation_input task 1 ─ 0..1 task_external_execution 1 ─ 0..1 test_connection_result

    입력 행과 실행 행은 판정에 쓰이는 도메인 데이터라 관찰 보존 정책으로 지우지 않습니다. 종단 실행 전체를 정리할 때 함께 제거합니다.

    원자성

    GET 저장과 미완료 상태는 한 커밋

    소유권(claim token) 확인 → 원문·digest 저장 → 같은 Task IN_PROGRESS 유지 → 후속 BLOCKED. 하나라도 실패하면 write-back 전체를 롤백합니다. 추천 입력의 DB 쓰기는 executor의 외부 호출 단계에서 하지 않습니다.

    POST 성공도 마찬가지로 Task DONE과 후속 READY 승격을 같은 커밋에 담습니다.

    모든 스키마는 JPA annotation(@Table/@Index/@UniqueConstraint)으로 선언합니다. Flyway나 손으로 쓴 SQL migration을 추가하지 않습니다. 실제 MySQL에서의 컬럼 타입·인덱스·길이 검증은 별도로 남아 있습니다.

    05

    연결 테스트는 “내가 시작한 실행”만 인정합니다
    
        
    가장 흔한 오해가 여기 있습니다. 시작 요청이 success=true로 접수됐다는 것과
        테스트가 성공했다는 것은 다른 사건입니다. 그리고 “가장 최근 실행이 성공”이라는 사실은 내 실행의 근거가 아닙니다.
    
      
    
    
    

    
    
      
    01 · 호출 전
    요청 키 고정
    Task 생성 시 test-connection:v1:task:{id}를 저장합니다. attempt가 바뀌어도 같은 키입니다.
    
      
    02 · 접수
    시작 · 실행 회수
    요청 키와의 상관관계가 증명된 응답에서 external version을 한 번 바인딩합니다. latest에서 처음 본 version을 그냥 쓰지 않습니다.
    
      
    03 · 관찰
    그 version만 폴링
    PENDING·RUNNING은 대기입니다. 기본 4초 간격이며, 전송 오류는 같은 attempt를 유지한 채 다시 관찰합니다.
    
      
    04 · 종결
    SUCCESS / FAIL
    같은 version의 SUCCESS만 Task DONE입니다. FAIL은 JOB_FAILED, 마감 초과는 EXECUTION_TIMEOUT 종결 실패입니다.
    
    
    

    
    deadline은 Task마다 “최초 READY”에 한 번만 고정됩니다
    
    
    앞 Task가 오래 걸렸다고 뒤 TC의 허용 시간을 깎지 않습니다. 대신 READY 이후의 큐 대기는 포함되고,
      재시도는 마감을 절대 연장하지 않습니다. 조건을 바꿔 보세요.
    
    
    
      
    
        
      
    
      
    
        
      
    
      
    
    
    
    
      
    
        
    
        
    00:00
    
        
    
      
    
    
    
    
    기본값은 pipeline.test-connection에서 옵니다 — execution-timeout PT50M,
      polling-interval PT4S, 접수 max-fail-count 24. 생성 시 Task 행에 고정하므로 설정을 바꿔도 실행 중 Task는 흔들리지 않습니다.
      BLOCKED 동안 deadline_at은 null이며, READY/IN_PROGRESS에서 마감이 유실되면 새 마감으로 복구하지 않고
      EXECUTION_INPUT_INVALID로 종결합니다.
    

    
    
      
    
        
    폴 전송 오류
    
        
    짧은 실패 횟수로 죽이지 않습니다
    
        
    일시적인 폴 전송 오류는 TaskType.handleCallFailure의 TestConnection 구현이 전용 poll 결과로 바꿔
          같은 attempt에서 다음 폴을 예약합니다. Task 이름 비교는 하지 않습니다.
          오류 횟수는 task_check·진단에만 남고 종결 판정에서 읽지 않습니다. 대기를 끝내는 것은 고정 deadline뿐입니다.
    
        
    반대로 401·403 같은 non-retryable 계약 오류는 즉시 종결합니다. 접수(시작) 오류만 기존 attempt 재시도 예산을 쓰되
          같은 요청 키로 같은 실행을 회수합니다. 실행 행이 유실돼도 새 테스트를 만들지 않습니다.
    
        
    이 Task 안의 재시도와 새 실행으로 다시 테스트하는 재시작은 다릅니다. 재시작은 새 task id·새 요청 키·
          다른 external version·자기 마감을 갖습니다 — §09에서 나란히 비교합니다.
    
      
    
      
    
        
    진단 조회
    
        
    정상 관측과 마지막 오류를 따로 보관
    
        
    GET /api/v1/pipelines/{pipelineId}/tasks/{taskId}/test-connection-result
    
        
    실행 행이 있으나 폴링 전이면 요청 키·바인딩된 version·마감만 200으로 돌려줍니다.
          종결 진단을 pending이나 통신 실패로 덮어쓰지 않고, 정상 본문과 마지막 오류를 각각 보관합니다.
          엔진의 판정은 typed 현재 poll 결과와 도메인 deadline만 사용하고 이 진단 테이블을 읽지 않습니다.
    
        
    last_error_operation이 null이면 호출 없는 사전검사 실패라
          오류 metadata 자체가 없습니다. 실제 폴 무응답은 operation이 있고 status/body만 null이라 구분됩니다.
    
      
    
    
    

    
    업무 완료 확인은 여전히 사람의 단계입니다.
      completion-status는 논리 DB 정책을 반영한 별도 업무 상태이고 acknowledgment는 사용자가 수행합니다.
      Task가 이를 자동 호출하지 않고, 테스트 성공 뒤 정책이 바뀌었다고 끝난 Task를 뒤집지도 않습니다.
    
    
    지금의 API로는 상관관계가 증명되지 않습니다.
      현재 시작 응답에는 success만 있고 화면은 latest version을 조회합니다.
      요청 키로 같은 실행을 회수하고 결과 version을 검증하는 계약, 이전 실행 중 신규 시작을 막는 보장을 확인하기 전에는 실제 실행을 열지 않습니다.
      version별 조회를 우선하며, latest 검증은 종결까지 다른 진입점이 실행을 덮어쓰지 못한다는 보장이 있을 때만 허용합니다.

        그 결과에서 created_at DESC, id DESC로 최신과 페이지를 고릅니다. 메모리에서 자르지 않습니다.

          유형 필터로도 갈리지 않으므로 id DESC가 최신을 결정하고, 최신은 항상 #106입니다.

    활성 실행의 유일성
    
        
    조회는 유형별이지만 활성 실행은 유형과 무관하게 대상당 하나입니다.
          RECONFIRM이 돌고 있으면 같은 대상의 TEST_CONNECTION을 동시에 시작할 수 없습니다.
          active_target은 모든 종단 경로에서 해제됩니다.
    
      
    
      
    
        
    완료 수의 의미
    
        
    완료/전체는 Task 개수입니다. API 호출 수도, 시간 기반 진행률도 아닙니다.
          추천 GET까지 끝났어도 그 입력 Task의 완료 수는 0입니다.
          전체 수는 Recipe의 Task 목록에서 옵니다 — 예시의 AWS_INSTALL_V1은 plan·apply 3쌍과
          네트워크 준비 확인을 합쳐 7개, AWS_RECONFIRM_V1은 Destroy 3개와 공통 Task 2개로 5개입니다.
    
      
    
    
    

    
    type을 Task 종류로 역추론하지 않습니다.
      CUSTOM에서 공통 입력 Task를 실행해도 유형은 CUSTOM입니다.
      그리고 “가장 최근 RECONFIRM이 DONE”이라는 사실만으로 현재 승인이 완료됐다고 판단하지 않습니다 —
      업무 소유 서비스가 승인·설정 버전과 pipelineId를 연결해 기록해야 합니다.
      잘못된 enum 값은 400, 결과 없는 latest는 기존과 같은 204입니다.
    
  
    

  
  
    
    
    
      
    08
    
      
    
        
    “고를 수 있다”와 “실행할 수 있다”는 다릅니다
    
        
    공통 Task는 모든 CSP에서 선택할 수 있습니다. 하지만 실제 실행은 설정과 client capability가 둘 다 있어야 열립니다.
        기본값은 닫힘입니다. 아래 조건을 켜고 꺼 보세요.
    
      
    
    
    

    
    
      
    
        
        
        
        
    
          
          
        
    
      
    
      
    
    
    

    
    활성화 전에 upstream에서 확인해야 하는 계약
    
    
      
      
    1. 서비스 주소·서버 계정 인증·응답과 맥락 검증·timeout
        
      없으면 해당 공통 operation의 실제 실행을 비활성으로 둡니다. 사용자 SSO 쿠키를 저장하거나 재사용하지 않습니다.
        호출 대상은 설치 업무를 소유한 서버 서비스이며, 프런트 Next.js API나 Terraform InfraManager API를 대용으로 호출하지 않습니다.
      2. 
      
    2. Task별 요청 키의 멱등성과 세대 보호
        
      같은 요청의 재시도가 같은 효과를 내야 하고, 이전 실행의 늦은 DELETE·POST가 다음 세대 정보를 훼손하지 않아야 합니다.
        Admin 직접 쓰기를 포함한 모든 진입점에 같은 보호나 동등한 직렬화가 있어야 합니다.
      3. 
      
    3. 삭제 후 추천 조회 가능 여부와 CSP 삭제 순서
        
      확정정보를 지운 뒤에도 해당 승인 버전의 추천을 조회할 수 있어야 합니다. AWS·IDC 삭제 순서와 자원 참조 보존은
        활성화 전에 확인합니다. 못 갖추면 그 CSP의 RECONFIRM만 비활성입니다.
      4. 
      
    4. TC 요청 키로 실행 회수 · version 검증 · 중복 실행 제한
        
      없으면 실제 연결 테스트 실행을 열지 않습니다. timeout은 “실행되지 않았다”는 증거가 아닙니다.
      5. 
      
    5. 업무 소유 서비스의 종단 상태 소비
        
      성공·최종 업무 실패·취소를 멱등하게, 재전달 가능하게 처리해야 합니다. 최종 업무 실패 시 승인 완료 정보를 제거하는
        기존 정책(ADR-006 D-007)을 유지하고 일시 retry·취소와 구분합니다. Slack 알림을 업무 콜백으로 쓰지 않습니다.
      6. 
    
    

    
    실제 adapter 없이 endpoint나 header를 발명해 활성화하지 않습니다.
      내부 executor·저장·fake 기반 테스트는 먼저 구현할 수 있고 실제로 구현했습니다.
      추천 응답의 승인·세대 맥락도 opaque JSON에 필드를 지어내지 않고, 실제 adapter가 원문과 함께 검증한 맥락을 반환해
      등록에 그대로 사용해야 합니다. 그 전까지는 client boundary의 typed 계약으로만 표현합니다.
      enabled-operations는 생성 검증에만 쓰며, 설정을 바꿔 실행 중인 Recipe를 재조립하거나 중단하지 않습니다.
      실행 중 capability가 사라지면 OPERATION_UNAVAILABLE 값으로 종결합니다.
    
  
    

  
  
    
    
    
      
    09
    
      
    
        
    다시 하는 길은 두 갈래이고, 둘은 같은 것이 아닙니다
    
        
    하나는 이미 있는 Task 안에서의 attempt 재시도입니다. 같은 정체성으로 같은 요청을 이어서 냅니다.
        다른 하나는 새 인프라 작업을 만드는 재시작입니다. 재시작은 지원되는 정상 경로이지만,
        끊긴 실행을 이어 붙이는 것이 아니라 정체성이 전부 새로 발급되는 별개의 실행입니다.
    
      
    
    
    

    
    
      
    
        
    A · Task 내부 재시도
    
        
    같은 실행 · 같은 Task · 같은 키
    
        
      
          
    • 같은 task id를 유지HTTP·TC 접수 재시도는 attempt 증가 · TC 폴 오류는 같은 attempt 유지
      • 
          
    • 같은 요청 키upstream 멱등성이 같은 요청임을 알아볼 수 있습니다
      • 
          
    • 고정된 입력 그대로추천 POST 재시도는 저장된 본문·digest를 재사용하고 GET을 다시 호출하지 않습니다
      • 
          
    • 같은 논리 실행 회수TC는 같은 요청 키로 같은 실행·같은 version을 되찾습니다
      • 
          
    • 마감 연장 없음TC의 최초 READY 마감은 재시도로 늘어나지 않습니다
      • 
        
    
        
    엔진이 알아서 합니다. 운영자가 다시 무언가를 만들지 않습니다.
    
      
    
      
    
        
    B · 새 파이프라인 재시작
    
        
    새 실행 · 새 Task · 새 키 · 선택된 뒷부분만
    
        
      
          
    • 새 인프라 작업 한 건기존 실행을 되살리지 않고 생성 경로를 그대로 탑니다
      • 
          
    • 복제 범위는 선택된 뒷부분(suffix)기본은 원본 체인의 첫 non-DONE Task부터 끝까지입니다. Recipe 전체를 다시 돌리지 않습니다
      • 
          
    • fromSequence는 더 앞으로만앞 단계를 포함시킬 수는 있어도 실패 지점을 건너뛸 수는 없습니다(뒤로 가면 400)
      • 
          
    • 유형·Recipe·계보는 승계type/recipe_definition을 그대로 물려받고 origin_pipeline_id·origin_task_id로 계보를 남깁니다
      • 
          
    • 새 task id → 새 요청 키키가 task_id에서 파생되므로 자동으로 전부 새 값입니다
      • 
          
    • 추천 실행 입력 중에서는 NLB 옵션만 승계“NLB만 이어받는다”는 추천 기반 입력 데이터에 한정된 말입니다 — 파이프라인 메타데이터 전반이 아닙니다. 원문·승인 맥락은 새 GET으로 다시 얻습니다
      • 
          
    • TC는 새 실행·새 version·새 마감자기 최초 READY 기준으로 마감을 새로 고정합니다
      • 
        
    
        
    생성 시점의 활성화 게이트(§08)를 다시 통과해야 합니다.
    
      
    
    
    

    
    
      
    
        정체성 축별 비교 · 무엇이 유지되고 무엇이 새로 발급되는가
        
    축A · Task 내부 재시도B · 새 파이프라인 재시작
    
        
          
    pipeline같은 실행이 계속 진행새 실행 · 이전 실행은 종결 상태 그대로 보존
    
          
    task id동일신규 · 단, 선택된 뒷부분의 Task만 새로 생성
    
          
    범위실패한 그 Task 하나기본 = 첫 non-DONE Task부터 끝까지 · fromSequence로 더 앞에서 시작 가능(실패 지점 건너뛰기는 불가)
    
          
    유형 / Recipe / 계보같은 실행이므로 그대로원본에서 승계 · origin_pipeline_id·origin_task_id로 계보 기록
    
          
    요청 키동일 (…:v1:task:{같은 id})신규 (…:v1:task:{새 id})
    
          
    추천 입력 스냅샷저장된 본문·digest 재사용 · GET 재호출 없음 · source_attempt_number 불변새 GET으로 새로 캡처 · 이전 스냅샷을 옮겨 오지 않음
    
          
    TC 외부 실행 / version같은 논리 실행을 회수 · 바인딩된 version 유지다른 실행 · 다른 version이 시작 시 새로 바인딩
    
          
    TC deadline최초 READY에 고정된 값 · 연장 없음새 Task의 자기 최초 READY 기준 새 마감
    
          
    가용성 검증이미 생성된 실행이라 생성 검증을 다시 하지 않음
    실행 중 capability가 사라지면 OPERATION_UNAVAILABLE로 종결    		provider·operation capability와 RECONFIRM 추가 계약 게이트를 다시 검증
    
          
    원래 외부 요청같은 키로 이어서 냄 · 멱등성은 upstream 책임취소됐다는 증거가 없음 · 아직 진행 중일 수 있고 중복 효과가 남을 수 있음
    
            
      
    
    
    

    
    
      
    
        
    정확한 예시 하나
    
        
    AWS RECONFIRM · 앞 4개 DONE, 입력 Task FAILED
    
        
    AWS_RECONFIRM_V1은 Task 5개(Destroy 3 → 확정정보 삭제 → 추천 기반 입력)입니다.
          앞 4개가 DONE이고 마지막 추천 기반 입력 Task가 FAILED로 실행이 종결됐다고 합시다.
    
        
      
          
    • 기본 재시작첫 non-DONE = sequence 5 → 새 실행에는 추천 기반 입력 Task 하나만 생깁니다. 유형은 그대로 RECONFIRM이고, 그 Task 안에서 새 GET → POST를 합니다
      • 
          
    • Task 개수새 실행의 완료/전체는 0 / 1에서 시작합니다. Destroy 3개와 확정정보 삭제는 다시 실행하지 않습니다
      • 
          
    • 여전히 Task 하나GET과 POST는 같은 Task 안의 두 단계입니다. 재시작해도 “추천 조회 Task”가 따로 생기지 않습니다
      • 
          
    • fromSequence로 더 앞을 고르면예를 들어 4를 고르면 확정정보 삭제부터, 1을 고르면 Destroy부터 다시 실행됩니다. 반대로 6을 고를 수는 없습니다 — 실패 지점을 건너뛰면 설치 완전성이 깨집니다
      • 
        
    
      
    
      
    
        
    재시작할 수 있는 실행
    
        
    대상의 최신 실행이면서 FAILED / CANCELLED일 때만
    
        
      
          
    • RUNNING · PENDING · DONEPIPELINE_NOT_RESTARTABLE · typed 409. 진행 중이면 취소가 먼저이고, DONE에는 재시작할 실패 지점이 없습니다
      • 
          
    • 종결됐지만 최신이 아님PIPELINE_NOT_LATEST · typed 409. 그 뒤에 이미 다른 실행이 있습니다
      • 
          
    • 최종 심판은 여전히 유니크 제약이 검사들은 best-effort 읽기이고, 동시 재시작·생성 경합은 삽입 시점의 active_target 유니크 제약이 막습니다
      • 
        
    
        
    진행 중인 실행에서도 Task 내부 재시도(A)는 정상 동작합니다 — 막히는 것은 B뿐입니다.
          아래 종결 사례들은 모두 “그 대상의 최신 실행”이라는 전제 위에서 읽어 주세요.
    
      
    
    
    

    
    상황을 고르고 두 갈래를 비교해 보세요
    
    
    같은 실패라도 어떤 상황에서는 A가 아예 불가능합니다. 종결된 실행은 이어서 진행할 수 없기 때문입니다.
    
    
    
      
    
        
      
    
      
    
        
        
      
    
    
    
    
    
      
    
      
    
      
    
    
    

    
    
      
    
        
    재시작해도 Task 모양은 그대로
    
        
    추천 조회는 여전히 별도 Task가 아닙니다
    
        
    새 실행의 CONFIRM_RESOURCES_FROM_RECOMMENDATION_V1도 Task 하나입니다.
          그 Task 안에서 새 추천 GET을 하고, 자기 task_confirmation_input 행에 본문을 write-once로 고정한 뒤 POST합니다.
          재시작을 위해 “추천 조회 Task”를 따로 만들지 않고, 이전 실행의 스냅샷을 복사해 오지도 않습니다.
    
        
    공통 Task는 ALL_CSP라 CUSTOM에 같은 정의를 여러 번 담을 수 있고,
          그때도 Task마다 요청 키·입력 행·재시도 예산이 독립입니다(§02). 재시작으로 만든 실행의 Task도 마찬가지로 독립입니다.
    
      
    
      
    
        
    재시작이 지우지 못하는 것
    
        
    DB 취소는 외부 취소가 아닙니다
    
        
    이전 실행의 취소·펜스(claim token, 종단 상태)는 DB 쓰기를 막는 장치입니다.
          이미 나간 DELETE·POST·테스트 시작 요청을 회수하지 못합니다. 재시작 시점에도 원래 요청이 upstream에서 진행 중일 수 있고,
          그 결과가 늦게 도착할 수 있습니다.
    
        
    그래서 재시작의 안전성은 upstream의 요청 키 멱등성과 세대 보호에 의존합니다(§08의 2번 계약).
          새 실행은 새 키를 쓰므로 이전 요청과 자동으로 합쳐지지 않습니다 — 두 요청이 모두 반영될 가능성을 화면과 운영 절차가 인지해야 합니다.
    
      
    
    
    

    
    재시작은 “확인 불가”를 “없던 일”로 바꾸지 않습니다.
      화면은 이전 실행이 어디까지 커밋했는지와 확인 불가한 외부 효과를 함께 보여 주고,
      재시작이 만든 실행은 별도 이력 행으로 남습니다(§07의 목록에서 각각 보입니다).
      대상당 활성 실행은 하나이므로, 이전 실행이 종결돼 active_target이 해제된 뒤에만 재시작할 수 있습니다.
