ADR · terraform-apply-approval-gate

인프라 변경 승인 게이트

지금 terraform은 무엇을 만들고 무엇을 지우는지 아무도 확인하지 않은 채 APPLY까지 자동으로 진행된다. PLAN과 APPLY 사이에 사람이 판단하는 단계를 하나 넣고, 그 판단에 필요한 정보를 콘솔과 Slack으로 함께 보낸다.

0 → 1

지금 무슨 일이 일어나고 있나

레시피는 *_TF_PLAN task가 성공하면 곧바로 *_TF_APPLY를 깨운다. plan이 산출한 변경 목록을 사람이 보는 지점이 파이프라인 어디에도 없다. 인프라 변경 중에는 되돌리는 비용이 큰 것들이 있다 — 리소스 삭제, 그리고 in-place 변경이 불가능해 삭제 후 재생성되는 replace가 대표적이다.

확인 지점을 넣지 못한 이유는 두 가지였다. 첫째, plan 원문은 수백~수천 줄이고 terraform 문법에 익숙한 사람만 읽을 수 있다 — 승인자에게 그대로 들이밀면 판단이 아니라 형식적 통과가 된다. 둘째, 서버가 private cluster에 있어 인터넷에서 들어오는 경로가 없다 — Slack 버튼 같은 외부 승인 수단을 붙일 방법이 없었다.

이 ADR은 두 문제를 함께 푼다. plan 로그를 집계와 리소스 목록으로 요약해 비전문가도 판단할 수 있게 만들고, Slack Socket Mode(아웃바운드 연결만 사용)로 인바운드 경로 없이 채팅에서 승인을 받는다.

바뀌는 것은 단계 하나

기존 실행 모델을 대체하지 않는다. PLAN과 APPLY 사이에 게이트 task 하나가 들어가고, 나머지 순서·재시도·취소 규칙은 그대로다.

현재 — 설치(INSTALL)

PLAN → APPLY → BDC PLAN → BDC APPLY

plan 결과는 저장되지만 아무도 읽지 않는다. 확인 없이 다음 단계로 승격된다.

이후 — 설치(INSTALL)

PLAN → 승인 대기 → APPLY → BDC …

승인되면 즉시 APPLY로 승격, 반려되면 파이프라인 전체 취소, 기본 24시간 내 응답이 없으면 만료된다.

현재 — 삭제(DELETE)

BDC destroy → service destroy

plan 단계 자체가 없다. 파괴 작업이 곧바로 시작된다.

이후 — 삭제(DELETE) · 로드맵 PR 4

destroy plan → 승인 대기 → BDC destroy → service destroy

승인은 첫 파괴 행위보다 앞에 있어야 의미가 있다. 순서를 재구성하고 destroy plan을 신설한다.

다섯 단계로 본 흐름

단계마다 누가 행동하는지를 함께 표시했다. Phase 2에서 늘어나는 것은 단계가 아니라 4단계의 행위자다.

STEP 1

요청

요청자

파이프라인을 생성하면서 요청자와 확인 요청 메시지를 함께 남긴다. 승인자가 "왜 이걸 지금 하는가"를 알 수 있게 하는 유일한 입력이다.

STEP 2

PLAN 실행

시스템

기존과 동일하게 terraform plan이 돌고 로그가 저장된다. 새로운 수집 경로가 없다 — 이미 저장 중인 로그를 그대로 쓴다.

STEP 3

승인 대기

시스템

plan 로그를 집계 + 리소스 목록으로 요약해 콘솔 카드와 Slack 메시지로 동시에 띄운다. 파이프라인은 여기서 멈춘다.

STEP 4

결정

관리자

승인 · 반려 · 만료(기본 24시간) 중 하나로 닫힌다. 콘솔 API와 Slack 버튼이 같은 처리 경로를 쓴다.

Phase 2 — 서비스 담당자로 확대
STEP 5

자동 진행

시스템

승인 즉시 APPLY가 승격된다. 반려면 파이프라인 전체가 취소되고, 만료면 실패로 닫힌다.

게이트 — 사람의 결정이 있어야 넘어가는 단계 Phase 2에서 넓어지는 지점(같은 단계, 넓어진 권한과 진입 화면)

승인자가 실제로 보는 것

두 표면은 같은 정보를 담는다 — 대상, 요청자, 요청 메시지, 요청 시각, plan 요약, 만료까지 남은 시간. Slack이 없어도 콘솔만으로 승인이 완결되고, 반대로 콘솔을 열지 않아도 Slack에서 처리된다.

무엇이 좋아지는가

사고 예방

되돌릴 수 없는 변경 앞에 사람이 선다

통제점 0개→1개

삭제·재생성처럼 복구 비용이 큰 변경이 확인 없이 실행되는 경로가 사라진다. destroy 게이트(PR 4)까지 적용하면 파괴 작업 전체가 같은 규칙 아래로 들어온다.

감사 완결

"누가 왜 요청했고 누가 승인했는가"가 남는다

실행 시각만→요청자 · 사유 · 승인자 · 시각

지금 기록되는 것은 실행 시각뿐이다. 이후에는 요청 맥락과 결정이 한 행에 남고, 콘솔·Slack 어느 경로로 승인했는지까지 구분된다. 사후 추적이 사람의 기억에 의존하지 않는다.

판단 가능성

terraform을 모르는 사람도 판단할 수 있다

plan 원문 수백 줄→집계 + 리소스 목록

승인이 형식적 통과가 되지 않으려면 승인자가 내용을 이해해야 한다. 요약을 신뢰할 수 없을 때는 수치를 보여주지 않고 "콘솔에서 원문 확인"으로 넘긴다 — 틀린 요약으로 승인을 받는 것이 최악이기 때문이다.

운영 부담

안전장치를 넣어도 느려지지 않는다

대기 = 자원 점유→점유 없음

승인 대기 중인 파이프라인은 terraform 실행 슬롯도, 동시 실행 캡도 쓰지 않는다. 승인을 기다리는 건이 늘어도 다른 작업의 처리량은 그대로다. 관리자는 콘솔을 열지 않고 Slack에서 바로 처리할 수 있어 대기 시간도 줄어든다.

도입 순서

설정 기본값이 꺼짐이라 배포 자체는 기존 동작을 바꾸지 않는다. 켜는 시점은 운영이 정한다.

PR 1

백엔드 코어

승인 상태·기록 테이블·게이트 task·승인 API·plan 요약 추출. 이 시점에 콘솔만으로 승인이 완결된다(Slack 없이).

PR 2

콘솔 UI

승인 대기 상태 표시, 승인 카드와 요청 맥락 표시, 생성 화면의 확인 요청 메시지 입력.

PR 3

Slack 승인(ChatOps)

Socket Mode 연결로 요청 발송·버튼 수신·결과 반영. private cluster에 인바운드 경로를 열지 않는다.

PR 4

삭제(destroy) 게이트

destroy plan 신설과 순서 재구성으로, 파괴 작업 전에도 같은 게이트를 세운다.

선행 — InfraManager destroy plan API 협의
Phase 2

서비스 담당자 승인

같은 4단계에서 승인 주체가 담당자로 넓어진다. 진입 화면은 콘솔의 TargetSource 상세페이지이며 권한 판정은 BFF가 담당한다 — 실행 구조는 그대로다.

가드레일

승인 게이트는 새로운 정지 지점이라, 잘못 만들면 파이프라인이 멈춰 서는 원인이 된다. 아래는 그걸 막기 위해 설계에 못박은 규칙들이다.

방치되지 않는다

기본 24시간이 지나면 요청은 만료되고 파이프라인은 실패로 닫힌다. 무기한 대기가 남지 않는다.

틀린 요약으로 승인받지 않는다

로그가 잘렸거나 파싱이 어긋나면 수치를 보여주지 않고 원문 확인으로 넘긴다. 확신할 수 있을 때만 숫자를 낸다.

Slack이 죽어도 승인은 된다

Slack 메시지는 표시일 뿐이고 진실은 DB에 있다. 채팅이 실패해도 콘솔에서 그대로 승인할 수 있다.

이중 처리가 없다

콘솔과 Slack에서 동시에 눌러도, 여러 서버가 동시에 받아도 최초 1건만 확정된다. 나머지는 "이미 처리됨"으로 응답한다.

Phase 1 적용 범위는 AWS·GCP의 서비스 단위 Apply 두 종류다. 화면은 설계 확정본을 옮긴 것으로, 실제 구현 시 세부 문구는 달라질 수 있다.
